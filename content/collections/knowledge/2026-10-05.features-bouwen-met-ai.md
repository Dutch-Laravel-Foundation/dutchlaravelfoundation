## Eerst een plan

Laat de agent bij een grotere taak eerst een plan maken, voordat hij code schrijft. Bespreek het plan en pas het aan. Een fout in het plan is goedkoop; een fout in de code niet.

Bewaar het plan als bestand in je repository, bijvoorbeeld `plan.md`. Laat het eindigen met een controle: welke test of welke check bewijst dat de taak af is? Een volgende sessie, of een andere agent, kan dan verder waar de vorige stopte.

## Beslissingen vastleggen in ADR's

Een plan gaat over één taak. Maar sommige beslissingen gelden voor het hele project: welke aanpak je kiest, of wat je bewust niet bouwt. Zo'n beslissing staat vaak alleen in een oude chat. Een nieuwe sessie weet er niets van. De agent stelt dan dezelfde vragen opnieuw, of kiest een richting die je al had afgewezen.

Leg zulke beslissingen vast in een ADR: een Architecture Decision Record. Een ADR is een kort bestand met vier onderdelen:

- **Context:** welk probleem speelde er?
- **Beslissing:** wat kies je, of wat kies je bewust niet?
- **Gevolgen:** wat betekent dat voor de code?
- **Herzien als:** wanneer kijk je er opnieuw naar?

Zet ADR's in één map, bijvoorbeeld `docs/adr`, en nummer ze: `0001-inertia-met-react.md`. Verwijs ernaar in `AGENTS.md`:

```md
Lees de ADR's in `docs/adr` voordat je een nieuwe package, een nieuw patroon of een nieuwe feature voorstelt.
```

Schrijf een ADR alleen voor een beslissing die een volgende sessie moet kennen. Niet voor elke pull request, en niet als dagboek. Een ADR ligt ook niet voor altijd vast. Verandert de situatie? Schrijf dan een nieuwe ADR die de oude vervangt.

Kent C. Dodds legt dit goed uit in zijn video [Turn Your Agent on Auto-Pilot with ADRs](https://www.youtube.com/watch?v=vRoqBBI51Vo){:target="_blank"}.

## Een werkwijze als skills

Je hoeft deze werkwijze niet zelf in skills te schrijven. Er zijn sets met algemene skills voor softwareontwikkeling. Twee bekende:

- **[Superpowers](https://github.com/obra/superpowers){:target="_blank"}** van Jesse Vincent: een complete werkwijze, van brainstormen en een plan schrijven tot TDD, systematisch debuggen en code review.
- **[mattpocock/skills](https://github.com/mattpocock/skills){:target="_blank"}** van Matt Pocock: losse skills die je zelf kiest, onder andere voor TDD, bugs zoeken en code review.

Vooral de skills voor het begin van een taak zijn waardevol. Ze laten je nadenken voordat de agent code schrijft:

- **brainstorming** (Superpowers): de agent vraagt door naar wat je wilt bereiken. Daarna stelt hij een ontwerp voor en wacht hij op je akkoord.
- **grill-me** (Matt Pocock): de agent ondervraagt je over je plan, tot elke beslissing duidelijk is. Bij elke vraag geeft hij zijn eigen advies.
- **grill-with-docs** (Matt Pocock): hetzelfde, maar de agent legt de uitkomst ook vast. Begrippen komen in een `GLOSSARY.md`. Belangrijke beslissingen legt hij vast als ADR in `docs/adr`. Een volgende sessie leest ze terug.

Beide sets zijn er als plugin voor Claude Code. De skills werken ook los, in elke agent. Installeer ze dan met [vercel-labs/skills](https://github.com/vercel-labs/skills){:target="_blank"} in `.agents/skills`:

```sh
npx skills add mattpocock/skills
```

Kies één manier: de plugin of de losse skills. Anders heb je elke skill twee keer.

Neem ook niet alles over. Deze sets zijn groot en kunnen botsen met je eigen regels in `AGENTS.md`. Begin met één of twee skills, en voeg pas meer toe als je ze mist.

> **Samen met je agent:** begin een nieuwe feature met "grill me". Beantwoord de vragen, en laat de agent daarna het plan in `plan.md` zetten.

## Een frisse blik

Laat werk van een agent controleren door een andere agent, in een nieuwe sessie. Die heeft geen last van de aannames uit de eerste sessie. Vraag hem de wijziging te vergelijken met het plan, en alleen echte fouten te melden. Anders stelt hij vooral verbeteringen voor die niemand nodig heeft.

Je CI is de laatste controle. Daar draait hetzelfde `composer check` als lokaal, inclusief je browsertests. Wat daar niet doorkomt, wordt niet gemerged.

## Agentic development environments

Concept, nog uit te werken. Tools waarin je met agents aan je project werkt: meerdere sessies naast elkaar, je app, je terminal en je review op één plek. Voorbeelden om te bekijken: Solo, T3 Code en OpenCode.
